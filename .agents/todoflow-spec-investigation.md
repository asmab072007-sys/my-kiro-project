### 3. AC-6: Filter Tasks — task-logic.js `filterTasks()`

```js
function filterTasks(tasks, filter) {
  if (filter === 'active') return tasks.filter(t => !t.completed);
  if (filter === 'completed') return tasks.filter(t => t.completed);
  return tasks;                    // 'all' falls through
}
```

AC-6 requires:
- `"Active"` → only incomplete tasks ✅ (`!t.completed`)
- `"Completed"` → only completed tasks ✅ (`t.completed`)
- `"All"` → all tasks ✅ (default return)

**Verdict: FULLY MATCHES AC-6.**

### 4. AC-7: Search Tasks — task-logic.js `searchTasks()`

```js
function searchTasks(tasks, query) {
  if (!query.trim()) return tasks;
  const q = query.trim().toLowerCase();
  return tasks.filter(t => t.text.toLowerCase().includes(q));
}
```

AC-7 requires:
- Case-insensitive match on task text ✅ (both query and text `.toLowerCase()`)
- Empty search returns all tasks matching current filter ✅ (`if (!query.trim()) return tasks`)
- Combination with filter is handled by `getVisibleTasks` which chains `filterTasks → searchTasks` ✅

**Verdict: FULLY MATCHES AC-7.**

### 5. `getVisibleTasks` composition

```js
function getVisibleTasks(tasks, filter, search) {
  return searchTasks(filterTasks(tasks, filter), search);
}
```

Filter is applied first, then search on the filtered result. This is correct behavior per AC-7: "tasks matching the current filter." When filter = 'all', `filterTasks` returns the full array and `searchTasks` handles the search, which is exactly the expected behavior.

**Verdict: CORRECT.**

## Bugs and Missing Features

### BUG-1 (Medium): `filterTasks` imported but never called directly in app.js

`filterTasks` and `searchTasks` are destructured in `app.js` but never called — `getVisibleTasks` handles both. They are dead imports in `app.js`. This is not a bug that causes incorrect behavior, but it is dead code. Low priority, but worth noting.

### BUG-2 (Medium): Edit does not update priority or due date

**Spec gap vs AC-4:** AC-4 only specifies editing task _text_, and the implementation correctly handles text editing inline. However, US-3 says "correct mistakes or update task details" — and there is no UI mechanism to change priority or due date after a task is created. The spec's AC-4 only tests text editing, so this is within spec, but it is a real usability limitation. No fix required unless the spec is updated.

### BUG-3 (Minor): `isOverdue` uses strict less-than comparison

```js
function isOverdue(task) {
  if (!task.dueDate || task.completed) return false;
  const today = new Date().toISOString().slice(0, 10);
  return task.dueDate < today;
}
```

A task due _today_ (dueDate === today) returns `false` (not overdue). This is a reasonable product decision, but it means a task due today is not highlighted as overdue until tomorrow. The spec (AC-9) says "due date in the past" — so this is technically correct per spec. Worth documenting as an intentional design choice.

### BUG-4 (Minor): No Enter key on Edit in some browsers (potential)

The `blur` event and `Enter` keydown event both call `saveEdit()`. Because `blur` fires when Enter is pressed (focus leaves), `saveEdit` could be called twice. The `{ once: true }` on the blur listener prevents double-save on blur-after-Enter in most browsers, but on Enter keydown, `e.preventDefault()` prevents form submission but the input still blurs after `render()` replaces the DOM. In practice this is harmless because `render()` rebuilds the DOM immediately, removing the edit input, so the blur listener never fires a second time. **No actual bug.**

### BUG-5 (Minor): No AC-10 Priority badge color in the spec

AC-10 specifies: green=low, yellow=medium, red=high. The CSS classes `priority-badge--low`, `priority-badge--medium`, `priority-badge--high` are generated in `createTaskElement`. Whether the actual CSS file implements these colors needs to be verified separately (not within scope of this investigation). The JS logic correctly applies the classes.
